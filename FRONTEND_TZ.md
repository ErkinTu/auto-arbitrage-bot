# ТЗ: показательный frontend аналитики автомобилей

## Цель

Сделать простой, демонстрационный frontend на Vue 3 для базы `car-analytics-mvp`, без экранов парсинга, синхронизации, нормализации и другой внутренней логики проекта.

Первое MVP работает только с фактическими данными, которые уже есть в базе. Оно не должно имитировать обученную модель, прогнозировать цену за пределами доступной выборки или скрывать нехватку данных. Все оценки, графики и аномалии считаются из текущих объявлений, истории цен и агрегированной статистики.

Frontend должен показать ценность собранной базы:

- общая статистика по автомобилям в базе;
- пошаговый FSM-сценарий выбора автомобиля;
- расчет оценочной стоимости по выбранной марке, модели и году;
- аналитическое окно результата с изображением карточки, средней ценой, диапазоном, аномалиями и графиком изменения цены по времени.

Это фундамент для следующего этапа, где поверх накопленных данных будут внедряться обученная статистика, ML-модели, оптимизация качества оценки, выбрасывание аномалий, кэширование готовой статистики и выдача конечному пользователю более точной итоговой оценки.

## Граница первого MVP

Первый MVP - это data-driven витрина, а не обученная система оценки.

Разрешено:

- считать средние, медианные, минимальные и максимальные цены по имеющимся объявлениям;
- строить графики по `daily_market_stats` и `listing_price_history`;
- показывать количество данных в выборке;
- показывать confidence на основе размера выборки;
- находить грубые аномалии простыми статистическими правилами;
- показывать пустые состояния, если данных недостаточно.

Не разрешено в первом MVP:

- обучать модель;
- выдавать прогноз там, где нет релевантных данных;
- делать сложную корректировку цены по параметрам, если она не подтверждена текущими данными;
- скрывать маленькую выборку за уверенной оценкой;
- заменять реальные данные моками в production-режиме.

## Технологии frontend

- Vue 3.
- TypeScript.
- Vite.
- Pinia для состояния FSM и кэша справочников.
- Vue Router, если будет больше одного маршрута. Для первого MVP достаточно одного маршрута `/`.
- Chart.js, ECharts или ApexCharts для графиков. Рекомендуется ECharts как гибкий вариант для line/bar charts и tooltip.
- CSS: обычные CSS modules/SFC styles или Tailwind, если команда уже готова его поддерживать.

## Что не входит в frontend MVP

- Управление парсером.
- Запуск синхронизации.
- Редактирование справочников, алиасов, поколений.
- Админка нормализации.
- Авторизация.
- CRUD объявлений.
- ML-модель оценки цены.

## Основной пользовательский сценарий

Пользователь открывает страницу аналитики и видит:

1. Сводную статистику по базе.
2. FSM-виджет выбора автомобиля.
3. После выбора марки, модели и года получает результат оценки.
4. В результате видит:
   - выбранный автомобиль, например `Toyota Camry, 2024`;
   - изображение из карточки объявления;
   - среднюю оценочную стоимость;
   - диапазон рынка;
   - количество объявлений в выборке;
   - уровень доверия;
   - список возможных ценовых аномалий;
   - график изменения средней цены похожих авто во времени, включая 2024, 2025 и 2026 годы, если такие данные есть в базе.

## Структура экрана

### Верхняя панель

- Название продукта: `Car Analytics`.
- Краткий статус базы:
  - всего объявлений;
  - активных объявлений;
  - объявлений, пригодных для аналитики;
  - дата последнего обновления.

### Блок общей статистики

Карточки метрик:

- `Всего объявлений`.
- `Активные объявления`.
- `Используются в аналитике`.
- `Марки`.
- `Модели`.
- `Средняя цена по базе`.
- `Медианная цена по базе`.
- `Последнее обновление`.

Дополнительные графики:

- Топ-10 марок по количеству активных объявлений.
- Распределение объявлений по годам выпуска.
- Распределение цен по диапазонам.
- Средняя цена по маркам.

### FSM-блок выбора автомобиля

FSM должен быть основным интерактивным элементом страницы.

Состояния:

```text
idle
  -> brand_selected
  -> model_selected
  -> year_selected
  -> loading_estimate
  -> result
  -> error
```

Шаги:

1. `Марка`
   - Список марок из базы.
   - Поиск по названию.
   - После выбора марки загружается список моделей.

2. `Модель`
   - Список моделей только выбранной марки.
   - Поиск по названию.
   - После выбора модели загружаются доступные годы.

3. `Год`
   - Список годов выпуска, которые реально есть в базе для выбранной пары `brand + model`.
   - Год должен выбираться из доступных значений, а не вводиться свободным текстом.

4. `Результат`
   - Запросить оценку и график.
   - Показать аналитическое окно.

Навигация FSM:

- Можно вернуться на предыдущий шаг.
- При изменении марки сбрасываются модель, год и результат.
- При изменении модели сбрасываются год и результат.
- При ошибке пользователь может изменить выбор без перезагрузки страницы.

## Аналитическое окно результата

Для примера `Toyota Camry 2024` показать:

### Summary

- Заголовок: `Toyota Camry, 2024`.
- Изображение из карточки объявления.
- Средняя оценка: например `$32 500`.
- Рыночный диапазон: например `$29 000 - $36 000`.
- Медиана рынка.
- Количество объявлений в выборке.
- Уровень доверия: `high`, `medium`, `low`.

### Изображение

Текущее поле `image_url` отсутствует в таблице `listings`, поэтому для MVP нужен один из вариантов:

1. Добавить нормализованное поле `image_url` или `image_urls` в `listings`.
2. Или вернуть изображение из `raw_payloads.payload`, если источник уже содержит URL фото.
3. Если изображения нет, frontend показывает нейтральный placeholder без ошибки.

Рекомендуемый контракт результата:

```json
{
  "representative_listing": {
    "id": 123,
    "title": "Toyota Camry 2024",
    "image_url": "https://...",
    "source_url": "https://..."
  }
}
```

### Аномалии цен

Показать объявления, которые сильно отклоняются от среднего рынка.

Для MVP достаточно правила:

- считать `q1`, `q3`, `iqr = q3 - q1`;
- низкая аномалия: цена `< q1 - 1.5 * iqr`;
- высокая аномалия: цена `> q3 + 1.5 * iqr`;
- если выборка маленькая, можно показывать предупреждение `Недостаточно данных для уверенного поиска аномалий`.

В UI показать:

- количество аномалий;
- минимальную и максимальную аномальную цену;
- таблицу 3-5 примеров: название, год, пробег, цена, город, ссылка на источник.

### График цены

График должен показывать динамику средней цены похожих авто во времени.

Минимальный вариант:

- line chart;
- ось X: дата или год/месяц;
- ось Y: средняя цена USD;
- tooltip: дата, средняя цена, количество объявлений;
- отдельная подпись, если данных нет.

Для сценария `Toyota Camry 2024` желательно уметь показать точки/агрегации за 2024, 2025 и 2026 годы, если история в `daily_market_stats` или `listing_price_history` доступна.

## Backend API для frontend MVP

Существующие API:

### `GET /api/v1/estimate`

Используется для базовой оценки.

Параметры:

- `brand`
- `model`
- `generation`, optional
- `year`
- `mileage_km`
- `customs_status`, optional

Для первого FSM, где пользователь выбирает только марку, модель и год, frontend может отправлять временный дефолт:

- `mileage_km=0` или медианный пробег по выборке.

Лучше доработать backend и сделать `mileage_km` optional для демонстрационного сценария.

### `GET /api/v1/price-trend`

Используется для графика.

Параметры:

- `brand`
- `model`
- `generation`, optional
- `year`
- `mileage_km`
- `days`

Для графика 2024-2026 нужен `days` до 1095 или отдельный endpoint с группировкой по годам/месяцам.

## Источники данных в базе

Основные таблицы:

- `listings` - текущее состояние объявлений.
- `brands` - марки.
- `car_models` - модели.
- `generations` - поколения.
- `listing_price_history` - история изменения цены.
- `daily_market_stats` - готовая дневная статистика.
- `raw_payloads` - исходный очищенный JSON, потенциальный источник image URL.

Главный фильтр для аналитики:

```sql
where
  listings.is_active = true
  and listings.analytics_eligible = true
  and listings.current_price_usd is not null
```

Frontend должен явно обрабатывать:

- загрузку общей статистики;
- пустую базу;
- нет моделей для выбранной марки;
- нет годов для выбранной модели;

- нет изображения;
- нет данных для графика;
- ошибка backend API;
- повторный выбор автомобиля.

Состояние:

```ts

  | 'idle'
  | 'brand_selected'
  | 'model_selected'
  | 'year_selected'
```

## Критерии приемки

- Страница открывается и показывает общую статистику базы.
- Пользователь может выбрать марку, модель и год через FSM.
- Списки FSM строятся только из данных, которые есть в базе.
- После выбора года отображается аналитический результат.
- В результате есть средняя цена, диапазон, количество объявлений и confidence.
- Если есть изображение, оно отображается; если нет, показывается placeholder.
- График цены отображает доступную динамику, а при отсутствии данных показывает понятное пустое состояние.
- Аномалии цен отображаются отдельным блоком.
- Frontend не содержит логики парсинга, запуска worker или администрирования нормализации.
- Все API-ошибки показываются пользователю без падения приложения.

## Следующий этап после первого MVP

После демонстрационного FSM система должна перейти от простых срезов по базе к полноценному аналитическому и оценочному контуру.

Основные направления:

- накопление обучающей выборки из объявлений и истории цен;
- подготовка признаков для оценки автомобиля;
- обучение моделей оценки стоимости;
- сравнение моделей и оптимизация метрик качества;
- автоматическое выявление и исключение сильных аномалий;
- кэширование часто запрашиваемой статистики;
- выдача конечному пользователю быстрой итоговой оценки с объяснимыми факторами.

Расширенные параметры оценки:

- пробег;
- объем двигателя;
- тип топлива;
- коробка;
- привод;
- кузов;
- город;
- статус растаможки;
- поколение;
- состояние/комплектация, если такие данные появятся.

Оценка должна перейти от простого среза `brand + model + year` к более точной модели похожести, статистическим корректировкам и обученной модели, которая учитывает параметры автомобиля и качество доступных данных.

Для production-выдачи важно:

- заранее считать и кэшировать тяжелые агрегаты;
- отделить online API для пользователя от offline pipeline обучения;
- хранить версию модели и дату последнего обучения;
- возвращать не только цену, но и диапазон, confidence, факторы влияния и предупреждения о слабой выборке.
