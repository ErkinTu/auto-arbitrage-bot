## 1. Уведомления: свежесть по дате ПУБЛИКАЦИИ, максимум 12 часов — СДЕЛАНО

Проблема: VIP-поднятые старые объявления (до сотен дней) всплывают в «свежей»
ленте; впервые увиденное = событие `new` = ложный пуш о «новинке».

Решение (Erkin): бот уведомляет ТОЛЬКО если `source_created_at` (дата публикации
на сайте, у lalafo это их unix `created_time`) не старше **12 часов**. В базу
старые объявления сохраняются как раньше — их цены нужны аналитике.

Реализация:
- Настройка `bot_max_listing_age_hours: int = 12` в `core/config.py` (+ .env.example).
- В `app/bot/matching.py::find_new_listings` добавить условие:
  `Listing.source_created_at >= utcnow() - timedelta(hours=...)`.
  NULL `source_created_at` = не уведомлять (пуш по неполным данным хуже тишины —
  это уже принцип `filter_matches`).
- Касается обоих источников (для mashina это тоже корректнее её `1d`-периода).
- Тест: объявление с created 13 часов назад не попадает в pending; 11 часов — попадает.

## 2. Раздельные задержки lalafo: лента 5с, карточки ~0.5с + защита от перегруза — СДЕЛАНО

Сейчас одна пауза `REQUEST_DELAY_SECONDS` (в проде 5с) после КАЖДОГО запроса —
и после ленты марки, и после каждой карточки. Карточки — лёгкие GET, 5с избыточно.

Решение (Erkin): делим. Лента (страница марки) — 5с; карточки — можно быстрее 1с,
но не перегружать сайт.

Реализация:
- Настройки: `lalafo_feed_delay_seconds: float = 5.0`,
  `lalafo_detail_delay_seconds: float = 0.5` (+ .env.example).
- В `LalafoParser.fetch_listings` спать feed-паузу, в `fetch_details` —
  detail-паузу (вместо общего `request_delay_seconds`).
- Предохранитель: при ответе 429 удваивать detail-паузу до конца работы парсера
  (инстанс живёт один цикл) — вежливый бэкофф, ретраи на 429/5xx уже есть.
- Ожидаемая длительность цикла: обычный ~80–90с (15 лент + единицы карточек);
  первый прогрев ~10–12 мин (15×5с + ~750×0.5с).
- Наслоения циклов НЕТ: поллер спит interval ПОСЛЕ завершения цикла
  (`polling_loop`), длинный первый прогрев просто сдвигает следующий цикл.

## 3. Статистика: свежесть выборки + автодеактивация «зависших» (30 дней) — СДЕЛАНО

У lalafo нет full-scan → проданные авто остаются `is_active=true` навсегда и
со временем портят аналитику устаревшими ценами.

Решение (Erkin), две части:
1. **SQL-фильтр свежести в статистике**: при построении агрегатов
   (`app/services/stats.py::rebuild_daily_market_stats`) учитывать объявления
   с `last_seen_at` не старше N дней. Настройка `stats_max_last_seen_days: int = 30`.
2. **Автодеактивация**: ежедневная задача — объявления, которые мы «не видели»
   в ленте больше 30 дней (`last_seen_at < now - 30d`), помечать
   `is_active=false, status='inactive', deactivated_at=now` + событие в
   `listing_status_history` (event_type='deactivated', details={'reason': 'stale'}).
   - Семантика именно last_seen_at (НЕ first_seen_at): активно висящее в ленте
     авто каждый цикл обновляет last_seen и продолжает жить.
   - Scope: можно ограничить lalafo-источником (у mashina своя деактивация
     через weekend full-scan), но правило безопасно и для mashina как страховка —
     решить при реализации, дефолт: только lalafo.
   - Где запускать: `app/worker.py` рядом с rebuild_stats (раз в сутки), чтобы
     работало даже когда бот выключен. Настройка `stale_listing_days: int = 30`.
   - История цен при этом сохраняется — аналитика прошлых дней не трогается.
- Тесты: деактивация по last_seen, недеактивация видимого вчера; фильтр стата.

# TODO: качество аналитики «ниже рынка» (решения Erkin, 2026-07-21)

Итерация про две реальные проблемы, найденные на проде 2026-07-21. Долгосрочный,
максимально устойчивый вариант (не «дешёвый костыль»). Разбор и обоснование — в
авто-памяти `below-market-fragility`.

## Контекст (что нашли на проде)

**Проблема 1 — выбросы цен раздувают среднюю.** Средняя рынка считается как
**mean**, верхнего порога адекватности цены НЕТ (есть только нижний
`MIN_PLAUSIBLE_PRICE_USD=500`). Пример: Honda Accord 2003 за **$520 000**
(`id=46003`, битый ввод) поднял mean группы Accord 2003 / bucket 200k+ с $6 782
(54 шт) до $16 113 (55 шт) → нормальная машина за $7 090 (= медиана) показывалась
как «−56.5% ниже рынка». Список топ-40 дорогих выявил **5 мусорных** записей:
Audi R8 2026 ×2 по $999 999 999 (плейсхолдер), Accord 2002 $630k, Camry 2002
$545k, Accord 2003 $520k. Легитимный верх рынка ≈ $500k (заказные G-Class AMG,
Maybach). **Вывод:** плоский порог не отличит «Camry 2002 за $545k» (мусор) от
«G-Class за $500k» (реально) — нужен И абсолютный предохранитель, И относительный
отсев по когорте.

**Проблема 2 — пустой пробег.** У **43% активных lalafo (2380/5590)** пробег =
NULL → попадают в изолированный bucket `unknown`, оторванный от парка mashina
(у которого пробег известен). Группа `unknown` редко набирает `min_samples=5`,
`market_average` → None. А **все широкие фильтры на проде — `below_market_only=True`**
(для них None = не пушить). Итог: свежие lalafo-авто с неизвестным пробегом почти
никогда не доходят до уведомлений, хотя аналогов на mashina десятки.

## ✅ Точечная чистка (сделано 2026-07-21)

5 мусорных объявлений (id 40289, 42797, 50699, 45255, 46003) деактивированы:
`is_active=false, status='inactive', analytics_eligible=false`, флаг
`price_implausibly_high`, событие в `listing_status_history`
(`reason=price_implausibly_high`), затем `rebuild-stats`. Средняя Accord 2003
очистилась (max по группе ≤ $8 700). Это разовая мера — ниже задачи A/B, чтобы
такое отсекалось автоматически.

## Задача A — абсолютный предохранитель цены на входе (защита для ВСЕХ потребителей)

Ловит явный мусор (плейсхолдеры $999 999 999, переполнения) ещё при нормализации,
единообразно с существующим `price_implausibly_low`. Выпадает и из статистики, и
из бота, и из `/estimate`, и с фронта — даже в группе из одной машины, где отсев
по когорте (задача B) бессилен.

Реализация:
- `app/services/normalizer.py`: константа `MAX_PLAUSIBLE_PRICE_USD = 2_000_000`
  (порог высокий: цель — только заведомо невозможное, реальный верх рынка ~$500k).
  В `normalize`/`normalize_lalafo` после расчёта `price_usd`:
  `if price_usd is not None and price_usd > MAX_PLAUSIBLE_PRICE_USD: flags.append("price_implausibly_high")`.
- `app/services/catalog_service.py`: добавить `"price_implausibly_high"` в
  `CRITICAL_QUALITY_FLAGS` (тогда `analytics_eligible=False` автоматически).
- Тест: цена $999 999 999 → флаг + `analytics_eligible=False`; $500 000 → чистая.

## Задача B — относительный отсев выбросов по когорте «модель+год» при ≥5 (ядро фикса)

Отвечает на вопрос «как определять верхнюю границу с учётом наших ≥5 авто».
Отсекаем цены, аномальные ОТНОСИТЕЛЬНО своей когорты — но только когда машин
достаточно, чтобы граница была осмысленной. Когорта — **модель+год целиком**
(а не bucket): один модельный год — связная ценовая группа (пробег двигает цену в
пределах ~2–3×, а не 100×), плюс это заодно чистит и bucket `unknown`.

Реализация в `app/services/stats.py::rebuild_daily_market_stats` — ПЕРЕД
раскладкой по бакетам:
- Сгруппировать отобранные listings по `(brand_id, car_model_id, year)`.
- Для когорт с `len >= OUTLIER_MIN_COHORT` (=5) посчитать median; исключить
  цены вне диапазона `[median / K, median * K]`, где
  `OUTLIER_PRICE_MEDIAN_MULTIPLE = 4.0` (K=4: сохраняет легитимный разброс по
  комплектациям/пробегу, но режет 70× мусор). Когорты <5 — не трогаем (полагаемся
  на задачу A).
- Из выживших строить бакетные агрегаты как сейчас.
- Настройки в `core/config.py`: `outlier_price_median_multiple: float = 4.0`,
  `outlier_min_cohort: int = 5` (+ `.env.example`).
- Тест: когорта из 6 машин ($6–8k) + 1 за $520k → $520k исключён из avg/median/
  sample_count; когорта из 3 машин с выбросом → выброс остаётся (мало данных).

Опционально (усилит бота): в `app/bot/matching.py::market_average` брать
`median_price_usd` вместо `avg_price_usd` — медиана и так почти не чувствительна к
остаточным выбросам. Дёшево, но после задач A+B уже не критично.

## Задача C — NULL-пробег: сравнивать по ВСЕМ бакетам модель+год

bucket `unknown` собирает NULL-пробеги машин с реально РАЗНЫМ пробегом → его
собственная средняя бессмысленна. Без пробега честнее сравнивать со всей годовой
когортой.

Реализация в `app/services/matching.py::market_average`:
- Если `listing.mileage_km is None` — НЕ добавлять условие
  `DailyMarketStat.mileage_bucket == ...`; агрегировать все бакеты этой
  модели+года (+растаможка), взвешивая по `sample_count` (логика суммирования уже
  есть). Для известного пробега — поведение без изменений.
- Эффект: Corolla 2003 → ~49 образцов вместо 2, порог ≥5 выполнен, бот оживает.
- ВАЖНО: делать только вместе с задачами A/B — иначе средняя по «всем бакетам»
  для NULL-пробега снова заражается выбросом из bucket `unknown`.
- Тест: listing с NULL-пробегом получает `market_average` по сумме всех бакетов;
  с известным пробегом — только по своему бакету.

## Задача D — вытащить пробег из lalafo (бэклог, лечение корня)

43% NULL — много. Часть пробега есть в заголовке/деталях карточки lalafo, парсер
его не достаёт. Добить извлечение (`app/parsers/lalafo.py` normalize + title-fallback)
снизит долю NULL, вернёт машины в нормальные бакеты, повысит точность оценки — тогда
задача C понадобится реже. Отдельная задача, НЕ блокирует C.
