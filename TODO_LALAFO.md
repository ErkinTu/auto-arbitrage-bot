## 1. Уведомления: свежесть по дате ПУБЛИКАЦИИ, максимум 12 часов — СДЕЛАНО

Проблема: VIP-поднятые старые объявления (до сотен дней) всплывают в «свежей»
ленте; впервые увиденное = событие `new` = ложный пуш о «новинке».

Решение (Erkin): бот уведомляет ТОЛЬКО если `source_created_at` (дата публикации
на сайте, у lalafo это их unix `created_time`) не старше **12 часов**. В базу
старые объявления сохраняются как раньше — их цены нужны аналитике.

Реализация:
- Настройка `bot_max_listing_age_hours: int = 12` в `core/config.py` (+ .env.example).
- В `app/bot/matching.py::find_new_listings` добавить условие:
  `Listing.source_created_at >= utcnow() - timedelta(hours=...)`.
  NULL `source_created_at` = не уведомлять (пуш по неполным данным хуже тишины —
  это уже принцип `filter_matches`).
- Касается обоих источников (для mashina это тоже корректнее её `1d`-периода).
- Тест: объявление с created 13 часов назад не попадает в pending; 11 часов — попадает.

## 2. Раздельные задержки lalafo: лента 5с, карточки ~0.5с + защита от перегруза — СДЕЛАНО

Сейчас одна пауза `REQUEST_DELAY_SECONDS` (в проде 5с) после КАЖДОГО запроса —
и после ленты марки, и после каждой карточки. Карточки — лёгкие GET, 5с избыточно.

Решение (Erkin): делим. Лента (страница марки) — 5с; карточки — можно быстрее 1с,
но не перегружать сайт.

Реализация:
- Настройки: `lalafo_feed_delay_seconds: float = 5.0`,
  `lalafo_detail_delay_seconds: float = 0.5` (+ .env.example).
- В `LalafoParser.fetch_listings` спать feed-паузу, в `fetch_details` —
  detail-паузу (вместо общего `request_delay_seconds`).
- Предохранитель: при ответе 429 удваивать detail-паузу до конца работы парсера
  (инстанс живёт один цикл) — вежливый бэкофф, ретраи на 429/5xx уже есть.
- Ожидаемая длительность цикла: обычный ~80–90с (15 лент + единицы карточек);
  первый прогрев ~10–12 мин (15×5с + ~750×0.5с).
- Наслоения циклов НЕТ: поллер спит interval ПОСЛЕ завершения цикла
  (`polling_loop`), длинный первый прогрев просто сдвигает следующий цикл.

## 3. Статистика: свежесть выборки + автодеактивация «зависших» (30 дней) — СДЕЛАНО

У lalafo нет full-scan → проданные авто остаются `is_active=true` навсегда и
со временем портят аналитику устаревшими ценами.

Решение (Erkin), две части:
1. **SQL-фильтр свежести в статистике**: при построении агрегатов
   (`app/services/stats.py::rebuild_daily_market_stats`) учитывать объявления
   с `last_seen_at` не старше N дней. Настройка `stats_max_last_seen_days: int = 30`.
2. **Автодеактивация**: ежедневная задача — объявления, которые мы «не видели»
   в ленте больше 30 дней (`last_seen_at < now - 30d`), помечать
   `is_active=false, status='inactive', deactivated_at=now` + событие в
   `listing_status_history` (event_type='deactivated', details={'reason': 'stale'}).
   - Семантика именно last_seen_at (НЕ first_seen_at): активно висящее в ленте
     авто каждый цикл обновляет last_seen и продолжает жить.
   - Scope: можно ограничить lalafo-источником (у mashina своя деактивация
     через weekend full-scan), но правило безопасно и для mashina как страховка —
     решить при реализации, дефолт: только lalafo.
   - Где запускать: `app/worker.py` рядом с rebuild_stats (раз в сутки), чтобы
     работало даже когда бот выключен. Настройка `stale_listing_days: int = 30`.
   - История цен при этом сохраняется — аналитика прошлых дней не трогается.
- Тесты: деактивация по last_seen, недеактивация видимого вчера; фильтр стата.
