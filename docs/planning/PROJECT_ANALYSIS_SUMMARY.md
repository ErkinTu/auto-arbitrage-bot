# Анализ новых требований и план интеграции

Дата анализа: 2026-10-04. Источники: `index.html` (кликабельный прототип бота), `sk_hunter_ux_razbor.md`, `sk_hunter_monetizaciya_sayt.md`, `ТЗ_что_починить_в_боте_до_прихода_80_тысяч.pdf`, сопоставлено с кодом `car-analytics-mvp` (FastAPI + aiogram + Postgres) и `analytics-front` (Vue 3 админка).

## 1. Краткое резюме (Executive Summary)

**Что такое `index.html`.** Это не шаблон сайта и не админка — это кликабельный прототип экрана Telegram-чата (имитация клиента Telegram в рамке телефона), написанный на чистом JS без фреймворка. Он один в один реализует сценарий из `sk_hunter_ux_razbor.md`: старт → сразу 5 карточек «ниже рынка» → «Хочу похожие» (фильтр создаётся автоматически по карточке, без мастера настройки) / «Не то» (карточка сворачивается в одну строку, а не в стену кнопок) → постоянное меню из 4 кнопок → пейволл после 3-го сигнала с двумя тарифами (помесячно и пожизненный «Основатель» со счётчиком свободных мест) → «Точный фильтр» как bottom-sheet с чипами и ползунками и живым счётчиком «38 машин за неделю». В файле также есть мёртвый код — встроенный скрипт `data-pplx-inline-edit` (строки 451–779), это служебный бридж Perplexity для редактирования внутри iframe, к продукту отношения не имеет, перед передачей в работу его нужно вырезать.

**Целесообразность.** Все три материала согласованы друг с другом: ТЗ (PDF) — это инженерный чек-лист «что чинить», UX-разбор — это новый сценарий интерфейса, `index.html` — кликабельный макет этого же сценария, монетизация — экономическое обоснование и верхнеуровневая дорожная карта. Делать стоит всё из блоков A/B ТЗ почти без изменений. Главный риск проекта — не в объёме работы, а в том, что **часть фундамента для новой карточки отсутствует физически**: в БД вообще не хранятся фото и описание объявлений (ни у mashina.kg, ни у lalafo.kg), хотя исходные фиды lalafo их отдают. Без этого поля ни одна из новых карточек (ни в боте, ни в Mini App, ни на сайте) не может быть photo-first, как того требуют все три документа. Это самая важная находка анализа — см. раздел 4, пункт 1.

**Объём работ.** Ориентировочно 230–310 часов (≈ 5–7 недель одного senior-разработчика) на блоки A+B из ТЗ, редизайн бота под `index.html`, Mini App и связанные доработки админки/бэкенда. Без блока A (A1–A7) трафик пускать нельзя — это 2–3 дня работы согласно самому ТЗ, и код подтверждает, что часть A4 (очередь отправки, 429) уже фактически готова.

## 2. Разбор и интеграция шаблона `index.html`

### 2.1 Концепция нового бота

`index.html` построен вокруг пяти механик, которых в текущем боте либо нет, либо они реализованы иначе:

| Элемент прототипа | Что это меняет в логике бота | Текущее состояние в коде |
|---|---|---|
| Старт → сразу 5 карточек, без вопросов | Онбординг не спрашивает ничего перед первой пользой | Сейчас `/add_filter` — 7-шаговый FSM (`app/bot/states.py` `AddFilter`), шаги «год», «пробег», «цена» требуют **текстового ввода** (`app/bot/handlers.py:562-643`), с кнопкой «Пропустить». Это прямо противоречит принципу «ноль ввода текстом» |
| «Хочу похожие» создаёт фильтр из карточки | Фильтр = производная от понравившейся машины (цена±20%, год±2, город, тип), а не ответы мастера | Такого эндпоинта/хендлера нет. Фильтр сегодня создаётся только через полный мастер `AddFilter` |
| «Не то» → карточка схлопывается в одну строку с «Вернуть» | Скрытие — лёгкое действие в потоке, а не стена кнопок | Кнопка скрытия есть (`block_menu_cb`, `handlers.py:407-462`), но список скрытого — это именно **стена кнопок «↩️ Вернуть: …»** (`blocks_kb`, `keyboards.py:196-203`), ровно то, что `sk_hunter_ux_razbor.md` называет проблемой «захламляет чат» |
| Постоянное меню (Лучшее сейчас / Мои запросы / Мой доступ / Помощь) | Reply-keyboard всегда внизу, а не команды | Частично есть: команды `/add_filter`, `/blacklist` существуют, но единого persistent-меню с этими 4 пунктами в коде не найдено |
| Пейволл на 3-м сигнале, с реальным примером | Таймер/счётчик показанных сигналов до предложения оплаты | Нет: оплата инициируется только явной командой, нет логики «после N сигналов показать пейволл» |
| «Мой доступ» — статус + оплата + честная отмена одним сообщением | Самообслуживание по подписке прямо в чате | Нет вовсе как пользовательского сценария бота — статус подписки сегодня виден только админу в `analytics-front` (UserDetailView), не самому пользователю в боте |
| «Точный фильтр» — bottom sheet с чипами/ползунками и live-счётчиком | Отдельный экран-калькулятор без текста | Нет; ближе всего — внутренний (админский) `MarketView.vue` с FSM марка→модель→год→пробег, см. 2.3 |

**Вывод:** `index.html` требует не косметики существующего мастера, а **новой модели диалога**: карточка как единица взаимодействия, автоматический вывод фильтра из лайка, и редактируемое «одно сообщение» вместо потока новых. Это согласуется с тем, что сам UX-документ предлагает как финальный шаг — перенести «Точный фильтр» в Telegram Mini App (веб-страницу), а не в чат-мастер.

### 2.2 Связь с админ-панелью

Текущая `analytics-front` — осознанно **строго read-only** панель (`docs/admin/ADMIN_PANEL_PLAN.md:170` — «строго read-only»), построенная для контроля качества данных и состояния пользователей, а не для управления продуктом. Новый сценарий бота добавляет сущности, которых в админке просто нет:

- **Счётчик мест «Основатель» (1412 из 2000).** Нужна новая таблица/поле и минимум read-only виджет в Overview — иначе никто в команде не увидит, сколько мест продано, кроме как через ручной SQL.
- **Источник/метка захода (`?start=hrd/ig/reel/market` из блока A1 ТЗ).** Сейчас `/start` разбирает **только** `ref_<code>` для рефералки (`app/services/referral.py:44-51`); универсальной метки канала нет ни в модели, ни в админке. Без этого поля нельзя посчитать ROI по роликам Хайриддина — ровно то, что требует A1.
- **Индекс уверенности / параметры сравнения** (мин. кол-во объявлений, пороги скидки). Сейчас это хардкод и env (`app/core/config.py`, `app/services/stats.py`), не видны и не редактируемы в админке. Решение см. в разделе 4, пункт 12.
- **Воронка по новым шагам.** Текущая воронка в Overview уже есть и уже обобщённая (рендерит `user_events` как % от старта, `OverviewView.vue:113-137`) — она построена так, что **добавление новых типов событий (`onboarding_complete`, `first_signal_sent`) не требует нового UI**, только новых записей в `user_events` на бэкенде. Это дёшево.
- **Очередь модерации SKUPKA Market + плашка «Проверено» (C4/C5 ТЗ).** Важная находка: `is_verified_seller` в текущей схеме — это **транзитный флаг с сайта-источника** (`app/models/entities.py:159`, проставляется нормализатором), а не бейдж, который ставит сама SKUPKA. Пользовательских объявлений (SKUPKA Market, @skupkakg_bot, ~11/день) в этом репозитории **нет вообще** — ни модели, ни очереди. Если это отдельный бот/сервис — это интеграционная задача между двумя системами, а не доработка `car-analytics-mvp`. Нужно уточнение у заказчика, где физически живут эти данные, прежде чем оценивать C4/C5 в часах.

### 2.3 Необходимые доработки бэкенда/API

Хорошая новость: публичная часть API в этом проекте **уже без аутентификации** по архитектуре (`CLAUDE.md`: «Публичная часть API без аутентификации… гейт только у admin/*»). Это именно то, что нужно и для Mini App, и для будущего публичного сайта — не требуется придумывать отдельную схему авторизации для гостевых витрин.

Нужно добавить/изменить:

1. **`GET /bot/cars/best`** — рейтинг «ниже рынка» для старта и «Лучшее сейчас» (сейчас это side-эффект push-рассылки, а не читаемый список по запросу).
2. **`POST /bot/filters/from-card`** — создать фильтр из параметров конкретной карточки (цена±20%, год±2, город, тип кузова). Новый метод, аналогов нет.
3. **`GET /bot/filters/preview-count`** — live-счётчик «38 машин за неделю» под ползунки Mini App. По сути это тот же запрос, что уже делает `vehicleFsm`/`marketApi.vehicleSummary()` в `analytics-front` (`api/market.ts`, `api/admin/catalog.py:54`) — рекомендуется переиспользовать сервис, а не писать новый расчёт.
4. **`GET/POST /bot/access`** — self-service статус/оплата/отмена для «Мой доступ» внутри бота (сегодня эти данные есть только в admin API, пользователю в чате недоступны).
5. **Telegram Mini App (WebApp) как отдельная публичная страница.** Технически это обычная веб-страница на HTTPS, открываемая кнопкой в боте. Разумный путь — не плодить третий фронтенд, а поднять её на той же связке Vue/Vite, что и `analytics-front` (там уже есть токены дизайна, `UiChart` на ECharts, тёмная тема, близкая к `index.html` по духу), но как **отдельный паблик-бандл без админской авторизации**, использующий уже открытые наружу публичные эндпоинты каталога/аналитики.
6. **`photo_url(s)` в модели `Listing`** — без этого поля ни один из вышеперечисленных эндпоинтов не отдаст фото, а вся новая карточка строится вокруг фото. См. раздел 4, пункт 1 — это блокер номер один.

## 4. Конфликты, риски и нерекомендуемые решения

### 1. Нет фото и описания в БД — фундаментальный блокер (High)
И `index.html`, и `sk_hunter_ux_razbor.md` строят всю новую карточку вокруг фото («Фото — главное в карточке», «если фото нет — лучше не отправлять»). Сегодня `Listing`/`NormalizedListing` не хранят ни `photo_url`, ни `description` вообще — нормализатор их не извлекает, хотя апстрим lalafo их отдаёт. **Альтернатива:** добавить поля и парсинг — это задача 1 в таблице, и она логически блокирует почти все UX-задачи (2, 3, 8). Делать её нужно первой, а не между прочим.

### 2. Автосписание (A6) конфликтует с задокументированным решением «Finik — разовая оплата» (High)
`docs/payments/PAYMENTS_FINIK_ANALYSIS.md:423` и `docs/payments/PRICING_PLAN.md` прямо фиксируют: «Автосписание/рекуррент… НЕ входит в итерацию», Finik используется как разовый платёж по QR/ссылке. Пользователь сегодня обязан вручную платить каждый период — это именно то, что ТЗ называет смертельным на 80 тысячах. Текущий ручной CLI-грант (`cli.py grant-subscription`) — рабочий, но не масштабируемый fallback для потерянных вебхуков, не основной путь.
**Альтернатива:** до начала работ выяснить у Finik, поддерживают ли они токенизацию/автоплатёж на практике (документация в коде может быть просто устаревшей), либо переходить на Freedom Pay, который ТЗ прямо называет поддерживающим «регулярные платежи и автоподписки». Оценка часов в таблице (п.15) намеренно плавающая — зависит от ответа провайдера, а не только от кода.

### 3. Apple/Google/Telegram Stars для цифровых подписок — не покрыто нигде (Medium, риск блокировки на мобильных)
В коде нет ни одного упоминания Telegram Stars/Apple/Google IAP. Само ТЗ требует отдельно уточнить у Freedom Pay/Finik, как они оформляют платёж, «чтобы бота потом не ограничили на мобильных». Это комплаенс-вопрос к провайдеру, а не чисто инженерная задача — закладывать время в план нельзя до ответа провайдера, но держать как потенциальный блокер публикации.

### 4. «Пробег обязателен» (B2) против текущего намеренного решения агрегировать null-пробег (Medium)
Сейчас объявления без пробега (≈43% ленты lalafo) **сознательно** агрегируются по всем бакетам пробега, а не отбрасываются — иначе lalafo почти никогда не наберёт `min_samples`. Буквальное исполнение B2 обрушит почти половину сигналов именно по источнику с и так более слабыми данными.
**Альтернатива:** не отбрасывать такие сигналы полностью, а помечать их низким индексом уверенности (идея самого `sk_hunter_monetizaciya_sayt.md`, п.5) и не показывать их платящим с порогом уверенности >70 — это решает обе задачи одним полем, без потери объёма сигналов.

### 5. Определение «перекуп» по повторному номеру телефона конфликтует с принципом приватности нормализатора (Medium, требует решения, не просто «сделать»)
`normalizer.py` явно и осознанно **не сохраняет** контактные данные продавца («Never retain seller identity/contact data»). B-блок ТЗ просит обратное — индексировать номера для детекции перекупов. Это разворот архитектурного решения, а не маленькая доработка, и несёт риск хранения персональных данных третьих лиц, взятых с чужих площадок.
**Альтернатива:** не хранить номер в открытом виде — считать перекупа по хэшу номера в короткоживущем индексе только на этапе синхронизации, никогда не персистить сырые цифры и не показывать их пользователю бота напрямую.

### 6. SKUPKA Market (модерация C4, бейдж «Проверено» C5) может быть вне этого репозитория (Low приоритет по часам, но High по риску недооценки)
В коде `car-analytics-mvp` нет ни одной сущности, относящейся к пользовательским объявлениям или боту @skupkakg_bot. Если это отдельная система — C4/C5 нельзя оценивать в часах без понимания границ интеграции. Рекомендация: уточнить у заказчика до начала спринта, иначе эти пункты рискуют стать неприятным сюрпризом в середине волны.

### 7. Публичный сайт с полным копированием объявлений конкурентов — уже сам документ клиента называет это риском (High, юридический)
`sk_hunter_monetizaciya_sayt.md` сам явно предупреждает: прямое копирование объявлений и фото с mashina.kg/lalafo.kg может привести к блокировке сбора данных и претензиям по авторским правам. Это не техническая, а юридическая развилка, и она совпадает по времени с задачей 1 (хранение фото) — проверку условий использования площадок нужно делать **параллельно**, а не после того, как фото уже начали заливать в продакшен.

### 8. Админка принципиально read-only — новые требования впервые просят писать (Medium, архитектурное решение)
`docs/admin/ADMIN_PANEL_PLAN.md` фиксирует read-only как осознанный выбор. Требования про видимость параметров алгоритма/мест «Основатель» можно и нужно сделать read-only виджетами (не нарушая инвариант), а не полноценными формами редактирования — иначе это первая брешь в сознательно выбранной архитектуре безопасности панели. Рекомендация — держать параметры алгоритма в env/CLI, в админке показывать только текущие значения.

### 9. Проверка по номеру телефона для триала (B7) против принципа «ноль трения за 30 секунд» (Medium, компромисс)
ТЗ прямо просит проверку триала «по идентификатору Telegram и по номеру телефона» — это требует экрана запроса контакта у Telegram, что добавляет трение именно в те первые 30 секунд, которые UX-документ и `index.html` всеми силами пытаются сократить до 3 нажатий. Сегодня дыра мультиаккаунта уже осознанно принята как есть (`docs/payments/PRICING_PLAN.md:234`).
**Альтернатива:** не запрашивать телефон на первом экране; делать это только перед вторым триалом (например, при активации реферального бонуса) — так антифрод работает именно там, где риск злоупотребления реален, не трогая новых пользователей.

### 10. Расхождение в числах между материалами клиента и документацией кода (Low, требует уточнения, не блокер)
`sk_hunter_monetizaciya_sayt.md` называет 131 545 активных объявлений; внутренняя документация кода (`docs/sources/SYNC_STRATEGY.md`) упоминает порядка 40 тысяч. Разница может объясняться периодом снятия скриншота или другим срезом метрики — стоит свериться перед тем, как использовать любую из цифр в презентации инвесторам/партнёрам.

## 5. Пошаговый план внедрения (Roadmap)

Порядок построен так, чтобы (а) не открывать трафик без блока A, (б) не строить photo-first карточки до появления фото в БД, (в) не продавать подписки до починки алгоритма.

| Этап | Содержание | Зависит от | Срок-ориентир |
|---|---|---|---|
| 0 | Юридическая проверка условий mashina.kg/lalafo.kg на использование фото — **запустить параллельно этапу 1**, не после | — | начать немедленно, 3–5 дней на ответ |
| 1 | Блок A целиком (A1–A7) — метка источника, кнопочный онбординг, порог отсечения, очередь/429 (в основном готово, нужен тест), тихие часы, мониторинг парсера | — | 2–3 дня (подтверждено самим ТЗ) |
| 2 | Хранение фото/описания (задача 1) + переключение `matching.py` на уже готовые поколение/медиану/пробег-бакеты из `daily_market_stats` (B1, задача 17) | Этап 0 (частично) | 3–4 дня |
| 3 | Новый бот-диалог по `index.html`: старт в 3 клика, фото-карточка, авто-фильтр из лайка, «Скрыто: X», постоянное меню, «Мой доступ» в чате | Этап 2 | 1.5–2 недели |
| 4 | Стоп-лист мусора (B3), дедупликация (B4), кнопка «Проверить эту машину» (B5), дайджест/частота (B6) | Этап 2 | 1 неделя, частично параллельно этапу 3 |

| 6 | Выяснить с провайдером (Finik/Freedom Pay) реальную поддержку автосписания и Stars-комплаенс → реализовать A6 | Можно начинать с этапа 1, код — после ответа провайдера | неопределённо до ответа, затем 3–5 дней |

| 10 | Публичный сайт MVP («Оценить машину» на базе уже существующего `MarketView`-FSM из `analytics-front`, цены рынка, лента с задержкой 24ч) | Этап 0 (юридически), этап 2 (данные) | 2–3 недели, можно параллельно с 6–8 |
| 11 | SKUPKA Market: модерация + плашка «Проверено» — **после уточнения границ системы** (см. раздел 4, пункт 6) | Уточнение у заказчика | TBD |
| 12 | Продажа 2000 пожизненных мест «Основатель» | Этапы 1–9, и только если триал→оплата вырос с текущих ~1.3% до заявленной клиентом контрольной цифры 5%+ | после проверки метрики, не по календарю |

**Контрольное правило запуска**, явно сформулированное в материалах клиента и подтверждаемое этим анализом: трафик пускать можно после этапа 1, **продавать** — только после этапов 1–9 и подтверждения конверсии триал→оплата ≥5%. Продажа мест «Основатель» до этого момента — финансово разовая и репутационно рискованная операция.
