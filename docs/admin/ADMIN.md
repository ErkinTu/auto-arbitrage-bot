# ADMIN.md — супер-пользователи (админы) бота

**Статус: ПЛАН.** Здесь — концепция и дизайн привилегированных пользователей и
их возможностей. Код ещё не написан; каждая идея сопровождается вариантами
реализации, гранями и рекомендацией. Реализовывать по мере приоритета.

---

## Концепция

**Супер-пользователь = админ бота** с расширенными привилегиями доставки
уведомлений (ранний пуш, повторный пуш на понижение). Это НЕ роль в Telegram-
группе (`access.py` проверяет членство для доступа к боту вообще) — это отдельный
флаг привилегий поверх обычного доступа.

**Ключевое правило назначения.** Админ назначается **только программистом,
прямым SQL-запросом к БД**. Осознанно:

- **Нет** бот-команды `/make_admin`, нет выдачи через интерфейс, нет
  «пригласительных». Привилегию нельзя получить или передать из UI —
  единственный путь наверх лежит через доступ к БД.
- Это граница безопасности: список админов меняется так же редко и
  контролируемо, как схема БД (тоже правится вручную, alembic в проекте нет).

## Модель данных (план)

Два варианта хранения:

| Вариант | Плюсы | Минусы |
|---|---|---|
| (A) флаг `is_superuser bool` на `bot_users` | одна проверка, джойн не нужен, tg_id уже там | смешивает роль с профилем |
| (B) отдельная таблица `bot_admins(telegram_id, note, granted_at)` | чистое разделение, аудит-поля | +таблица, +джойн в матчинге |

**Выбран (A) — СДЕЛАНО 14.08.2026:** флаг `is_superuser boolean not null default
false` на `bot_users` (`models/entities.py`). Проще всего: `bot_users` уже хранит
`telegram_id`, а матчинг уже джойнит `BotUser`, так что флаг доступен без лишнего
запроса. Аудит (кто/когда назначил) на текущем масштабе избыточен — при желании
добавить `superuser_note`/`superuser_granted_at` позже.

Флаг завели под админ-панель (`docs/admin/ADMIN_PANEL_PLAN.md`), но он ровно тот же,
что нужен идеям 1 и 2 ниже, — второй раз его вводить не придётся.

**Прода это не касается руками:** ALTER лежит в `db/session.py::_upgrade_postgres_schema`
и применяется сам при рестарте контейнера. Отдельно накатывать ничего не нужно.

```sql
-- то, что выполнится автоматически:
ALTER TABLE bot_users
  ADD COLUMN IF NOT EXISTS is_superuser boolean NOT NULL DEFAULT false;
```

### SQL-рецепты назначения (единственный способ)

```sql
-- Назначить админом по telegram_id
UPDATE bot_users SET is_superuser = true  WHERE telegram_id = <TG_ID>;

-- Снять
UPDATE bot_users SET is_superuser = false WHERE telegram_id = <TG_ID>;

-- Список текущих админов
SELECT telegram_id, username, first_name FROM bot_users WHERE is_superuser;
```

> Если пользователь ещё ни разу не писал боту, строки в `bot_users` нет —
> назначать после первого `/start` (строка создаётся в `get_or_create_bot_user`).

## Идея 1 — ранняя доставка уведомлений (приоритет админам)

**Цель.** Супер-пользователи получают пуш **на 5 минут раньше**, остальные — с
задержкой. Настройка `bot_notification_delay_minutes: int = 5` (0 = все
одновременно, как сейчас).

**Проблема с текущей архитектурой.** Сейчас `match_new_listings` пишет
`sent_notifications` и сразу возвращает `pending`, а `poller.polling_loop`
тут же шлёт всё через `send_notifications`. Матчинг и доставка не разделены,
цикл — раз в `bot_fresh_interval_minutes` (10 мин). «На 5 минут раньше» без
разделения этих фаз не выразить.

**Варианты реализации (ранжировано):**

1. **Отложенная доставка через очередь (рекомендация).** Разнести «матч» и
   «отправку»:
   - В `sent_notifications` (или новую таблицу `pending_deliveries`) добавить
     `deliver_after timestamptz`. При матче: админам `deliver_after = now`,
     остальным `deliver_after = now + delay`.
   - Отдельный проход доставки каждый цикл шлёт всё, у чего `deliver_after ≤ now`.
   - Плюс: точная, устойчивая к рестартам задержка; естественно расширяется на
     «тиры» доставки. Минус: заметная переработка (запись матча ≠ момент
     отправки; дедуп-инвариант «строка = уже отправлено» надо пересмотреть на
     явный статус `queued|sent`).

2. **Двухфазный цикл (лёгкий компромисс).** В одном цикле: сматчить всё → сразу
   отправить только админам → обычные пуши придержать и отправить в конце
   задержки. Требует, чтобы поллер просыпался с гранулярностью ~5 мин (отдельный
   delivery-тик или уменьшить интервал). Проще очереди, но задержка «плавает» в
   пределах тика и теряется при рестарте.

3. **Разнести по интервалу (грубый минимум).** Админам матчить и слать в цикле T,
   обычным — «догонять» те же объявления в цикле T+delay. Почти без нового кода,
   но точность = гранулярности цикла, и легко рассинхронизировать с дедупом.

**Грани для любого варианта:**
- Задержка должна быть **меньше** `bot_new_lookback_minutes` (сейчас 180) —
  иначе отложенное объявление выпадет из окна кандидатов раньше отправки.
- `sent_notifications` дедуплицирует по `(user, listing)` — отложенные пуши уже
  «зафиксированы», повторов между циклами не будет.
- Правило свежести (`bot_max_listing_age_hours`) считается в момент **матча**, а
  не отправки — 5-минутная задержка на него не влияет.
- Ночное окно: доставка должна работать в тех же `[bot_active_start_hour,
  bot_active_end_hour)`; отложенный под конец окна пуш — либо дослать в последний
  тик, либо в первый тик следующего дня (решить явно).

## Идея 2 — повторный пуш на дальнейшее понижение (только админам)

Ранее (разбор в диалоге) обсуждали общий кейс: кто уже получил пуш по
объявлению, **не увидит дальнейшего падения цены** — дедуп `(user, listing)`
жёсткий (в коде `already_sent` + `UniqueConstraint` в `sent_notifications`).
Решение — разрешить один повторный пуш на значимый спад — **делаем привилегией
супер-пользователей.**

**План:**
1. **Схема:** добавить `notified_price_usd numeric` в `sent_notifications`
   (последняя отправленная цена) и **снять** `UniqueConstraint(user_id,
   listing_id)` — сейчас он физически блокирует вторую строку. Прод — ручной
   ALTER/DROP CONSTRAINT.
2. **Логика в `match_new_listings`:** для события `price_changed`, если пара уже
   слалась — пускать повторно **только если `is_superuser`** И
   `current_price ≤ notified_price × (1 − bot_renotify_drop_percent/100)`
   (напр. 10%). После отправки обновлять `notified_price_usd`.
3. **Анти-спам:** порог 10% + кап повторов на объявление (1–2), чтобы «пила»
   цены не долбила чат даже админу.

**Почему только админам:** снятие `UniqueConstraint` убирает защиту от дублей
для всех — ограничив повторный пуш ролью, мы держим риск в узком, доверенном
круге и не рассылаем «стало ещё дешевле» всей аудитории (её первый пуш уже
сказал «ниже рынка»).

**Зависимость:** идея 2 требует флага `is_superuser` (модель данных выше);
идею 1 не блокирует и наоборот — их можно делать в любом порядке.

## Принципы (сквозные)

- **Привилегия не выдаётся из UI** — только SQL. Ни команды, ни кнопки.
- **Fail-safe по умолчанию:** отсутствие/`false` флага = обычный пользователь.
  Любая ошибка проверки роли трактуется как «не админ».
- **Приватность интересов:** ранняя доставка/повторный пуш не должны раскрывать
  обычным пользователям, что кто-то привилегирован (никаких общих лент, помечающих
  админов).
- **Наблюдаемость:** логировать число админ-пушей и отложенных обычных пушей за
  цикл — чтобы видеть, что задержка работает и не копит хвост.
