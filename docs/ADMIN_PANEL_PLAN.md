## 2. Принятые решения

| Вопрос | Решение |
|---|---|
| Вход в админку | **Telegram-бот**: `/admin` → одноразовая ссылка → сессия в БД (не JWT, см. §3 A4). Роль — флаг `is_superuser` на `bot_users` (вариант (A) из `docs/ADMIN.md`) |
| Первая итерация | **Операционка: просмотр базы + пользователи со статусами.** Аналитика цен и управление парсерами — следующими итерациями |
| Режим итерации 1 | **Строго read-only.** Ни одной ручки, меняющей данные |
| Форм-фактор | **Mobile-first.** Телефон — основной сценарий, десктоп получается расширением, а не наоборот |

Выбор входа и mobile-first сходятся удачно: ссылка приходит в Telegram, а
Telegram у владельца в телефоне — вход в один тап там, где админка и будет
открываться чаще всего.

**Следствие выбора входа, которое надо принять явно:** ссылка из Telegram
подразумевает публичный адрес, то есть админка выходит в интернет. Значит
**auth — единственная граница безопасности** над боевой БД, и делать его надо
до, а не после первой полезной страницы. Компенсации — в §3 и §8.

## 3. Этап A. Контур доступа

### A1. Роль — СДЕЛАНО 14.08.2026

Поле `is_superuser` на `BotUser` (`models/entities.py`). Назначение — **только
SQL**, как зафиксировано в `docs/ADMIN.md`: ни команды, ни кнопки. Этот же флаг
потом бесплатно закрывает обе идеи из `ADMIN.md` (ранняя доставка, повторный
пуш) — делаем один раз здесь.

**Ручной ALTER на проде не нужен** (уточнение к первой редакции плана): в
проекте есть идемпотентный авто-апгрейд `db/session.py::_upgrade_postgres_schema`,
который выполняется при каждом `init-db`, то есть на старте контейнера. Новая
колонка добавлена туда; новые таблицы `create_all` создаёт сам. Alembic
по-прежнему нет, но и ручного шага в деплое не появляется.

```sql
-- назначить админа (единственный способ)
UPDATE bot_users SET is_superuser = true  WHERE telegram_id = <TG_ID>;
-- снять
UPDATE bot_users SET is_superuser = false WHERE telegram_id = <TG_ID>;
-- список
SELECT telegram_id, username, first_name FROM bot_users WHERE is_superuser;
```

### A2. Одноразовые токены входа — СДЕЛАНО 14.08.2026

Таблица `admin_login_tokens` (`models/entities.py`), создаётся `create_all`:

| Колонка | Смысл |
|---|---|
| `user_id` | FK `bot_users` |
| `token_hash` | sha256 от токена — **сам токен в БД не хранится** |
| `expires_at` | +5 минут от выдачи |
| `used_at` | NULL = не использован; одноразовость |
| `created_at` | аудит |

Почему таблица, а не подписанный stateless-токен: одноразовость и отзыв. Ссылка
уезжает в мессенджер — она обязана сгорать после первого обмена.

### A3. Бот: `/admin` — СДЕЛАНО 14.08.2026

- Хендлер в `app/bot/handlers.py`; **не** в меню команд (`bot/commands.py`) —
  привилегия не должна светиться в автодополнении у всех. Тест-сторож
  `test_bot_commands.py` требует явно занести её в `INTENTIONALLY_HIDDEN`.
- Не `is_superuser` → отвечать ровно тем же, чем на любую неизвестную команду.
  Существование админки не подтверждаем. Отсюда **порядок регистрации**:
  хендлер стоит последним, уже после фолбэков визарда. Вне визарда неизвестная
  команда остаётся без ответа — и `/admin` у не-админа тоже молчит; внутри
  визарда неизвестная команда получает «выберите вариант кнопкой» — и туда
  `/admin` просто не доходит, отвечает тот же фолбэк. Цена: админу внутри
  визарда нужен сначала `/cancel`; это дешевле утечки.
- Выключатель: `ADMIN_PANEL_URL` пуст → команда молчит даже для админа.
- Генерация: `secrets.token_urlsafe(32)`, в БД — хэш, в чат — ссылка
  `https://<ADMIN_DOMAIN>/login?t=<token>`.
- Пересылку ссылки уже глушит `bot/protection.py` (protect_content ставится
  централизованно в middleware) — отдельного кода не нужно.
- Бот пишет токен в БД напрямую (`bot/db.py`), API читает оттуда же. HTTP между
  ботом и API не появляется — архитектурное правило «бот не ходит в API»
  сохраняется.

### A4. API: сессия — СДЕЛАНО 14.08.2026

```
POST /api/v1/admin/auth/exchange  {token}  → Set-Cookie: httpOnly, Secure, SameSite=Strict, 12h
GET  /api/v1/admin/auth/me                 → {telegram_id, username, first_name, session_expires_at}
POST /api/v1/admin/auth/logout             → 204
```

**Отступление от плана: сессия — строка в БД, а не JWT.** Подписанный токен дал
бы ровно один плюс — не ходить в базу, — но у API сессия и так открыта на каждый
запрос. Платой были бы: новая зависимость (PyJWT в проекте нет), секрет
`ADMIN_JWT_SECRET` в окружении и невозможность выйти — JWT живёт до `exp`, и
отозвать его нечем. Таблица `admin_sessions` отзывается удалением строки, а
снятый флаг `is_superuser` обрывает уже открытую сессию на следующем запросе.
Хранится sha256, как и у ссылки входа.

- `Depends(current_admin)` (`api/admin/deps.py`) — единственная точка гейта на
  **всех** `/api/v1/admin/*`; fail-safe: любое сомнение = 401, без объяснения
  причины наружу (в логе причина есть).
- Выключатель — `ADMIN_PANEL_URL` (он же нужен боту для ссылки). Пусто → роутер
  не подключается в `main.py` вовсе: ручек admin/* просто не существует, 404.
  Второй переменной под секрет не понадобилось.
- Rate-limit на `exchange`: 10 попыток / 5 минут на IP, счётчик в памяти
  процесса. В БД его держать не стоит — это готовый способ раздуть её мусором.
- `logout` намеренно **без** `current_admin`: требовать живую сессию, чтобы её
  погасить, — значит на протухшей вернуть 401 вместо выхода и оставить куку.
- CSRF в итерации 1 не нужен: только GET + `SameSite=Strict`. Появится первая
  write-ручка — вводим CSRF-токен тем же коммитом, не позже.
- Грабля тестов: кука помечена `Secure`, поэтому `TestClient` обязан жить на
  `https://` — иначе клиент не вернёт её, и «вошёл и хожу» молча превратится в
  «вошёл и везде 401».

### A5. Публикация (Caddy)

Отдельный блок на **отдельном** домене `ADMIN_DOMAIN` (не смешивать с
`PAYMENTS_DOMAIN`: `Host` входит в подпись вебхука Finik, домен платежей не
трогаем вообще):

```
{$ADMIN_DOMAIN} {
	handle /api/v1/admin/* { reverse_proxy api:8000 }
	handle { root * /srv/admin; try_files {path} /index.html; file_server }
}
```

- Наружу — только `/api/v1/admin/*` и статика. `estimate`, `catalog`, `/docs`
  остаются недоступными снаружи, как сейчас.
- `api` остаётся на `127.0.0.1`, `API_HOST` не меняем.
- Статика: сборка `analytics-front` (`pnpm build` → `dist/`) кладётся на сервер
  и монтируется в контейнер `caddy` как `/srv/admin`. Отдельный веб-контейнер не
  заводим — лишний сервис на 2 ГБ памяти.
- Профиль compose: Caddy уже под `payments`. Админка добавляет второй домен в
  тот же Caddyfile → профиль остаётся один, но в `DEPLOY.md` появляется шаг
  «залить dist» и требование DNS-записи для `ADMIN_DOMAIN`.
- Порты 80/443 в Lightsail уже открыты (нужны были Let's Encrypt для payments).
- CORS не нужен: фронт и API — один origin. `CORS_ORIGINS` остаётся как есть,
  для локальной разработки через Vite-прокси.

### A6. Проверка этапа

Снаружи: `/` даёт логин-страницу; `/api/v1/admin/users` без куки → 401;
`/api/v1/estimate`, `/docs`, `/api/v1/catalog/brands` → 404. Изнутри сервера
`curl 127.0.0.1:8000/health` по-прежнему отвечает. Ссылка из бота срабатывает
один раз, вторая попытка обмена → 401.

## 4. Этап B. Админ-API, итерация 1 (read-only)

Новый пакет `app/api/admin/` + `app/services/admin/`. Общие правила: `limit` с
жёстким потолком 200, ответ `{items, total, limit, offset}`, сортировка только
по индексированным колонкам, никаких N+1.

| Эндпоинт | Содержимое |
|---|---|
| `GET /admin/listings` | Фильтры: source, brand_id, model_id, year_from/to, price_from/to, city, is_active, analytics_eligible, normalization_status, поиск по title. Сортировка: last_seen_at / first_seen_at / price. Пагинация |
| `GET /admin/listings/{id}` | Все поля + `listing_price_history` + `listing_status_history` + quality_flags; raw payload — по явному флагу запроса |
| `GET /admin/users` | telegram_id, username, access_status, trial_expires_at, subscription_expires_at, число фильтров/блоков/платежей, последняя активность. Фильтр по статусу, поиск по id/username |
| `GET /admin/users/{id}` | Карточка: **чем именно** даётся доступ (группа / подписка / триал — через `bot/db.py::decide_access_status`, без дёрганья Telegram), фильтры, чёрный список, платежи, события воронки, рефералы, число отправленных пушей |
| `GET /admin/stats/funnel?days=30` | Воронка `start → trial_started → trial_expired → payment_created → paid`. Логику вынести из `cli.py` в сервис, CLI переключить на него же |
| `GET /admin/ops/parser-runs` | Последние прогоны по источникам: mode, статус, счётчики, ошибка. Ответ на «почему нет новых объявлений» |
| `GET /admin/overview` | Плитки главной: сводка базы + активные юзеры по статусам + свежесть последнего прогона |

Отдельно — **правка существующего** `GET /api/v1/market/vehicle-summary`:
добавить необязательный `mileage_km`. Сейчас эндпоинт пробег не принимает
вовсе, поэтому FSM во фронте заканчивается годом и показывает медиану когорты.
При этом `/api/v1/estimate` пробег принимает и умеет им пользоваться
(`analytics.py`: выборка ±50 000 км, линейная регрессия `_linear_estimate`,
поле `used_mileage_window`) — то есть в UI живёт более слабая из двух оценок.
Компромисс был отмечен ещё в `docs/FRONTEND_TZ.md` («лучше доработать
backend») и с тех пор не снят. В ответ добавить окно выборки, число объявлений
в окне и поправку на пробег: без них число в UI — гадание. При NULL-пробеге
поведение как в боте (`bot/matching.py::market_average`) — агрегируем все
бакеты и честно помечаем ответ «без поправки»; у lalafo пробег отсутствует
примерно у 43% объявлений, это не крайний случай, а норма.

Индексы под новые списки проверить отдельно: сортировка по `last_seen_at` и
фильтр по `city`/`normalization_status` уже покрыты, `bot_users` по
`access_status` — нет (при нынешних объёмах терпимо, но замерить).

Тесты: `TestClient` на каждый список — 401 без куки, 200 с кукой, потолок
`limit`, корректность `total`. Гейт важнее данных: он и есть граница.

## 5. Этап C. Фронт → админ-панель (mobile-first)

### Маршруты

```
/login          обмен токена из ссылки, редирект в /
/               обзор (плитки + свежесть данных + воронка кратко)
/listings       лента объявлений с фильтрами
/listings/:id   карточка + история цены
/users          лента пользователей
/users/:id      карточка пользователя
/market         подбор и оценка: марка → модель → год → пробег → результат
```

Шаг «пробег» — **новый, четвёртый**: существующий FSM обрывается на годе.
Пресеты повторяют бакеты `stats.py::mileage_bucket` (<50k, <100k, <150k,
<200k, выше), ввод числовой (не ползунок — пробег знают точно), «неизвестен» —
полноценный вариант, а не пропуск шага. Результат показывает не только цену,
но и как она получена: медиана когорты, поправка на пробег, окно выборки,
число объявлений в окне, и точечный график «цена ↔ пробег» с отметкой
выбранного значения.

Router guard: перед входом на защищённый маршрут — `auth/me`, 401 → `/login`.

### Что переиспользуется без переписывания

`VehicleFsm`, `VehicleResult`, `PriceTrendChart`, `PriceAnomaliesTable`,
`DashboardSummary`, `BrandStatsChart`, весь `src/ui/`, токены темы, `lib/format`.
FSM изначально пошаговый — на телефоне он работает лучше, чем на десктопе, и
менять его не нужно.

### Что добавляется

- `AppShell`: нижняя навигация (моб.) / сайдбар (десктоп), топбар с текущим
  разделом и выходом.
- `UiListRow` (строка-карточка ленты), `UiSheet` (нижняя шторка фильтров),
  `UiBadge` (статусы доступа), `UiSearch` (липкий поиск), `UiTable` — **только**
  для десктопа, как альтернативная раскладка тех же данных.
- `src/api/admin.ts`, `src/types/admin.ts`, сторы `listings`, `users`, `auth`.
- `http.ts`: `credentials: 'include'` + единый перехват 401 → `/login`.

### Порядок сборки

Auth-контур и `/login` → `/users` (данных мало, быстрее увидеть, что гейт,
лента и подгрузка работают) → `/listings` (тяжёлый список) → `/` → перенос
`/market`.

## 6. Дизайн: mobile-first

### Принцип

Проектируем под **360–430 px** (телефон в руке), десктоп получаем добавлением
колонок. Обратный порядок не работает: таблица на 12 колонок не «сжимается» в
телефон, она в нём умирает. Брейкпоинты Tailwind: база = моб., `md:` (768) —
планшет/десктоп, `lg:` (1024) — широкая раскладка. Третьего не заводим.

### Навигация

| | Моб. (<768) | Десктоп (≥768) |
|---|---|---|
| Разделы | нижний таб-бар, 4 иконки: Обзор / База / Юзеры / Рынок | сайдбар слева, фиксированный |
| Заголовок | липкий топбар: название раздела + действие справа | топбар с хлебными крошками |
| Фильтры | кнопка → нижняя шторка на весь экран, «Применить» внизу | панель фильтров над лентой |
| Карточка (`/:id`) | отдельный экран, кнопка «назад» | сплит: лента слева, карточка справа (по возможности, иначе тот же экран) |

Нижний таб-бар, а не бургер: большой палец достаёт до низа экрана, до верхнего
левого угла — нет. `env(safe-area-inset-bottom)` учитываем, иначе на iPhone
таб-бар уедет под системную полосу.

### Данные: лента вместо таблицы

Строка списка на телефоне — карточка в две-три строки, где видно **главное**, а
не всё:

```
┌────────────────────────────────────┐
│ Toyota Camry 2024        $32 500   │
│ Бишкек · 45 000 км · mashina       │
│ ● активно     обновлено 2 ч назад  │
└────────────────────────────────────┘
```

- Первая строка — идентификация + число, ради которого смотрят.
- Вторая — контекст мелким приглушённым.
- Третья — статус бейджем + свежесть.
- Остальные 20 полей — на экране карточки, не в ленте.

Для пользователей та же схема: `@username` + статус-бейдж, ниже — когда
истекает доступ, фильтров N, платежей M.

Пагинация на телефоне — **«Показать ещё»** (кнопка, не бесконечный скролл):
позиция не теряется при возврате из карточки, и не улетает случайный запрос при
скролле. На десктопе — она же плюс отображение `total`.

### Тач и размеры

- Минимальная зона нажатия 44×44 px, между строками ленты — реальный зазор,
  а не только рамка.
- Базовый кегль 16 px (меньше — iOS зумит поле ввода при фокусе).
- Числа — табличными цифрами (`font-variant-numeric: tabular-nums`), иначе
  колонка цен «пляшет».
- Никакого горизонтального скролла страницы. Что не влезает (широкая таблица на
  десктопной раскладке, график) — скроллится **внутри своего контейнера**.

### Визуальный язык

Наследуем `src/assets/styles/tokens.css` (там уже светлая/тёмная тема) и
достраиваем семантику статусов — статус пользователя должен читаться цветом
за полсекунды, но **не только** цветом:

| Статус | Смысл | Подача |
|---|---|---|
| `member` | член закрытой группы | нейтральный бейдж |
| `subscriber` | оплачено | акцентный, с датой окончания |
| `trial` | триал идёт | предупреждающий, с остатком дней |
| `revoked` | доступа нет | приглушённый |

Цвет + текст + форма бейджа вместе: на солнце экран телефона выцветает, и
различать статусы только оттенком нельзя. Тёмная тема обязательна (админку
открывают ночью с телефона) — обе темы задаются токенами, компоненты цвета
не хардкодят.

### Графики на телефоне

ECharts уже подключён (`UiChart`). Правила: высота фиксированная (200–240 px),
подписи оси прореживаются, tooltip по тапу, легенда убирается в подпись под
графиком. График, который не читается на 360 px, на главную не попадает —
вместо него плитка с числом и дельтой.

### Состояния

Для каждой ленты обязательны четыре экрана, а не один: загрузка (скелетоны
карточек, не спиннер по центру), пусто, «ничего не найдено по фильтру» (с
кнопкой сброса) и ошибка API с кнопкой «повторить». Это уже требование
`FRONTEND_TZ.md`, здесь оно просто распространяется на новые экраны.

### Оффлайн и сеть

Телефон = нестабильная сеть. Минимум: единый перехват сетевой ошибки в
`http.ts` с понятным сообщением и повтором. PWA/оффлайн-кэш в первой итерации
**не делаем** — read-only админка без сети бесполезна, а сложность заметная.

## 9. Риски и границы

- **Публичный вход к боевой БД.** Компенсации: read-only итерация 1, потолок
  `limit`, выключатель `ADMIN_PANEL_URL`, наружу проксируется только
  `/api/v1/admin/*`, роль выдаётся только SQL.
- **Утечка ссылки входа.** TTL 5 минут + одноразовость + protect_content.
  Украденная ссылка после первого входа мертва.
- **Схема без alembic.** Оказалось не проблемой: колонка `is_superuser` лежит в
  идемпотентном `_upgrade_postgres_schema`, таблицу `admin_login_tokens` создаёт
  `create_all` — оба применяются сами при рестарте, ручного шага в деплое нет.
  Цена: порядок применения нигде не записан, и откат схемы делается только
  вручную. Пока изменений единицы — терпимо.
- **Память сервера.** 2 ГБ на 4 сервиса; тяжёлые списки без потолка и без
  индексов могут задеть бот. Отсюда `limit ≤ 200` и запрет на «выгрузить всё».
- **Фронт без репозитория.** До первого коммита кода — единственная копия
  работы лежит в рабочем каталоге. Решение владельца; риск фиксируем здесь.
